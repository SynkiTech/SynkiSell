   161→   161→
   162→   162→Build one multi-tenant application with three distinct operational layers.
   163→   163→
   164→   164→### Layer A: SaaS platform administration
   165→   165→
   166→   166→Used exclusively by authorised platform administrators to manage the SaaS itself.
   167→   167→
   168→   168→Responsibilities include:
   169→   169→
   170→   170→- Registering and reviewing customer businesses.
   171→   171→- Managing deployment and subscription fees.
   172→   172→- Managing plans and permitted features.
   173→   173→- Monitoring payment status and annual renewal dates.
   174→   174→- Managing customer support and technical issues.
   175→   175→- Viewing platform-level operational metrics.
   176→   176→- Configuring AI provider settings and usage limits.
   177→   177→- Managing security settings and platform-wide announcements.
   178→   178→- Reviewing operational audit events within authorised access boundaries.
   179→   179→
   180→   180→### Layer B: Individual business workspace
   181→   181→
   182→   182→Each customer business receives an isolated workspace with:
   183→   183→
   184→   184→- Business profile and branding.
   185→   185→- Pharmacy department.
   186→   186→- Supermarket department.
   187→   187→- Shared POS.
   188→   188→- Inventory and purchasing.
   189→   189→- Suppliers.
   190→   190→- Staff accounts and permissions.
   191→   191→- Expenses and financial reports.
   192→   192→- AI business intelligence.
   193→   193→- Subscription and account settings.
   194→   194→
   195→   195→The first release supports one active store location per business. Design the data model so the product can support multiple locations in a future phase, but do not build full multi-branch operations now.
   196→   196→
   197→   197→### Layer C: Local POS operation
   198→   198→
   199→   199→The POS must prioritise transaction speed, barcode scanning, accurate stock movements, receipt printing, and resilience to temporary internet outages.
   200→   200→
   201→   201→Design an offline-capable POS architecture using appropriate local persistence, such as IndexedDB, and a controlled synchronisation queue.
   202→   202→
   203→   203→For the first release, support a clearly defined single-terminal offline sales mode. Do not claim reliable shared-stock operation across multiple disconnected terminals until the appropriate local networking, conflict resolution, and synchronisation functionality has been implemented and tested.
   204→   204→
   205→   205→Keep cloud-hosted business management separate from the local transaction interface where appropriate.

   924→   924→- Retry failed synchronisation safely.
   925→   925→- Make server-side processing idempotent.

   927→   927→- Provide clear indicators for online, offline, pending, and failed transactions.

  1135→  1135→## 17. WORKING METHOD
  1136→  1136→
  1137→  1137→Use a disciplined, iterative development process.
  1138→  1138→
  1139→  1139→At the start of each checkpoint:
  1140→  1140→
  1141→  1141→1. Review the existing requirements and current project state.
  1142→  1142→2. Identify the files, schema changes, dependencies, and tests needed.
  1143→  1143→3. Implement the smallest coherent set of functionality.
  1144→  1144→4. Run the relevant checks.
  1145→  1145→5. Fix failures before moving to dependent modules.
  1146→  1146→6. Update the documentation.
  1147→  1147→7. Record completed work and remaining limitations.
  1148→  1148→8. Commit tested, coherent milestones to the specified GitHub repository when GitHub access is available.
  1149→  1149→9. Verify the result of each commit and push operation. Never claim a successful push without confirmation.
  1150→  1150→
  1151→  1151→Maintain a visible implementation checklist in the repository.
  1152→  1152→
  1153→  1153→Use Git branches or commits at sensible milestones when the environment supports them.
  1154→  1154→
  1155→  1155→If a migration, architectural change, or security decision could destroy data or weaken isolation, stop that particular operation and explain the risk instead of proceeding blindly.
  1156→  1156→
  1157→  1157→Do not repeatedly regenerate the entire application. Preserve stable working modules and extend them deliberately.
  1158→  1158→
  1159→  1159→Do not ask the user to configure optional integrations before they are needed. Use mock providers and test credentials for local development where appropriate, without falsely representing mock operations as real transactions.
  1160→  1160→
  1161→  1161→Never commit environment files containing actual secrets. Before pushing, check the Git status and staged changes for credentials, private database URLs, API keys, and other sensitive information. Do not use force-push to bypass conflicts or repository protections.
